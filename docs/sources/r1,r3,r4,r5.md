## 1. 范围判断：九类中选择哪几类

### 1.1 “非推理、非感知”应怎样解释

不宜按字面声称某个视频 pipeline 没有感知或推理：OCR 需要感知，排序和集合差集也是广义推理，摘要需要语义抽象。因此，建议将本阶段目标改写为：

> **固定模型能力，不训练新的感知或推理模型；主要通过观察调度、证据保存、覆盖检查和可执行归约，减少“没找到、没看全、忘了、重复算、证据混了”的错误。**

这与“专门解决看不清细粒度动作、复杂遮挡追踪、隐含因果、物理反事实或空间重建”不同。分类标准是主控制流程与预计瓶颈，而不是题名里是否出现 Recognition、Reasoning、Counting。

| 类别 | 本阶段是否建设 | 本阶段允许的任务 | 不应混入的任务 |
|---|---|---|---|
| R1 定向定位与局部取证 | 是，复用 P01 基线 | 定位后直接读文字、属性、物体或短片段事实 | 全范围计数、否定穷举、跨时段身份轨迹、隐含原因 |
| R2 连续动态与实体状态追踪 | 不作为新增主类 | 仅允许轻量局部状态检查作为组件 | 遮挡身份传播、复杂动作正反、旋转相位、细轨迹 |
| R3 事件账本与时序归约 | 是，核心新增 | 可观察事件的次数、顺序、起止、首次/末次、时长 | 主要难点是极细微运动识别的混合样本不计入“组织型核心集” |
| R4 清单构建与集合归约 | 是，核心新增 | 可辨认对象/文字/类别的唯一计数、集合比较、缺失项核对 | 严重遮挡或外观完全同质导致不可确认身份的样本 |
| R5 分段全局综合 | 有条件建设 | 事实性梗概、整体活动概括、基于可见内容的体裁判断 | 隐喻、动机、笑点解释、叙事因果或价值寓意 |
| R6 证据约束关系推理 | 否 | 可复用本阶段的证据服务 | 因果、意图、人际关系、语义违例解释 |
| R7 假设与未来推演 | 否 | 可复用已观察事实 | 未见未来、干预条件下的结果 |
| R8 视觉符号与约束求解 | 不作为本阶段独立主类 | 已定义的加减、排序、集合基数等算子可共享 | 变量绑定、公式推导、复杂约束求解的完整 pipeline |
| R9 空间场景建模与查询 | 否 | 简单同框关系读取仍可由 R1 做 | 跨视角几何、参考系变换、尺度恢复、路线推导 |

**计数口径：四类主模板 = R1、R3、R4 三个核心模板 + R5 一个有条件的综合模板。新增完整设计是 R3、R4、R5 三类，不是另外发明三组平行的小 pipeline。** 原来的九类体系不变，本表只决定当前实现范围。[F01]

### 1.2 题目级的三种瓶颈标记

原生标签之外，开发集建议增加一个仅用于评估分组的字段：

```text
organization_core：局部证据足够清晰，主要难点是定位、覆盖、记忆、归约。
mixed：组织流程重要，但细粒度感知、身份识别或语义推断同样关键。
perception_or_reasoning_dominant：提供正确局部证据后，模型仍反复失败。
```

这个字段不作为运行时 oracle。测试集不能根据答题成败事后挑选“核心集”；应在开发阶段制定可复核的标注规则，并在正式测试前固定样本范围。

例如，“浇水发生几次”可以是 R3，但动作短到当前采样看不见时仍是混合难题；“房间里有几张桌子”可以是 R4，但视角绕回且桌子同质时，重识别会成为主要瓶颈。R3/R4 标签本身不保证问题容易。

### 1.3 四个模板的本质区别

| 主模板 | 需要持续维护的状态 | 最终主要操作 | 典型停止依据 |
|---|---|---|---|
| R1 | 一个有限、局部的事实包 | 读取/核验直接事实 | 已取得区分候选答案的局部证据 |
| R3 | 事件及其时间边界账本 | count / order / first / last / duration | 对当前时序操作必需的范围与边界已审查 |
| R4 | 规范化的对象、类别或事实集合 | unique count / union / difference / membership | 集合范围已审查，身份及负证据问题已处理 |
| R5 | 覆盖相关范围的分段事实与可追溯摘要 | 事实性合并与概括 | 分段覆盖满足策略要求，主要陈述可回查 |

停止依据都是**策略层面可审计的证据条件**，不是对模型观察完全正确、没有任何漏检的数学保证。

## 2. 现有 P01 能否作为 R1

### 2.1 判断：可以，但应命名为 R1 的视觉基线，而不是 R1 全覆盖实现

建议保留现有 `P01VideoAgent` 和旧 `--strategy p01` 行为，给评测注册表增加映射：

```text
pipeline_family = R1
implementation = p01-v2
input_profile = visual_only
evidence_topology = single_contiguous_span
implementation_commit = bfa02dadb4e09bfbab598e8cafaa46cdcf5576d4
```

这是一种**注册与评测映射建议**，并不表示仓库现在已经有 `--strategy r1` 命令。

现有代码的目标正是：上游已经确认题目适合本类，对一个视频进行局部取证，不负责顶层题型路由。入口拒绝独立图片和外部字幕，只接受单个视频；README 明确不支持音频和外部知识。[G01][G03]

所以：

- 可以作为 R1 中“纯视觉、一个连续局部片段足以直接回答”的实现。
- 不能声称已覆盖 R1 中需要音频、外部字幕或其他历史媒体接入的部分。
- 不能仅更改名字，就把原来范围表里的 18 个原生类别全部算作 R1 已支持。
- 不能把“一个短片段”误解为“一个静态帧”。P01 的 `dynamic_action` 仍可用于普通短事件取证；真正要求动作逆序、连续身份状态或细轨迹的题目，主类应为 R2。[G01][F01]

### 2.2 当前真实控制流程

下面是仓库文档及 `agent.py` 主流程一致描述的结构，不是新方案：[G01][G02][G03]

```text
Question
  -> ObservationCompiler（首轮不看选项）
  -> 分层 Locator（首轮不看选项）
  -> 最多两个 CandidateScout（首轮不看选项）
  -> 确定性选择一个连续局部证据段
  -> 编译去标签选项判别条件
  -> 至多一次 routine refinement
  -> InitialDecision
  -> 根据证据情况触发至多一次 bounded rescue
  -> FinalDecision / 确定性合法选项回退
```

自由文本题共享定位和取证，终局由 Composer 生成文本。全局 rescue overview 只负责定位，不可直接作为最终答案证据；不相交候选片段不能拼接成同一个证据包。默认最多 20 次模型调用，并为终局保留 2 次。[G02][G05]

### 2.3 适合保留的部分

| 现有机制 | 保留原因 | 向其他类复用时的限制 |
|---|---|---|
| 模型接口 `BaseVideoModel` | 不需要为每个角色加载新模型 | 共享模型实例，仍需全局调用预算 |
| 导航索引与源帧提取 | 分离便宜定位与高质量局部观察 | Top-2 候选搜索不能代替全范围扫描 |
| 带帧引用的事实与证据包 | 支持回查模型究竟看过什么 | 新增账本必须保留来源，不只保留文本 |
| 明确媒体预算与有限 rescue | 避免无限循环及资源失控 | 新类不能为每个窗口各自分配一份完整 P01 预算 |
| 终局合法答案与支持度分开 | 兼容 benchmark 必答，同时保留诊断 | 合法答案不等于已证实，空观察不等于零次/不存在 |
| 首轮选项盲 | 减少按照选项倒推视觉事实的机会 | 选项提供目标集合的题型需另定义受控信息协议 |

具体接口和类型依据 `[G03]`、`[G06]`、`[G08]`、`[G10]`。**应复用观察基础设施，不应让 R3/R4/R5 对每个窗口调用一次完整 `P01VideoAgent.solve()`。** 完整 P01 会选择单段并结束答题，不能自然充当不丢信息的账本观察器。

### 2.4 需要优先修正的边界：SearchHint 不等于 AllowedScope

这是本次从代码看到的风险，不是新实验发现的失败率。

`control.py::parse_question_interval()` 会把下列表达转换成具体区间：

```text
at the beginning / intro / title card -> 开头最多 15 秒
at the end / near the end             -> 结尾最多 15 秒
credits                              -> 结尾最多 20 秒
around 某时间                        -> 该时间前后各 5 秒
```

`reconcile_interval()` 没有把这些启发式提示与题目明确给出的数值区间分开；主流程将合并后的结果作为 `explicit_span` 使用。因此，“开头”等模糊提示可能变成不允许越界的硬范围，甚至与结构化 `given_interval` 发生冲突。[G04][G03]

建议拆为三个字段：

| 字段 | 来源 | 是否可以阻止读取帧 |
|---|---|---|
| `allowed_scope` | benchmark 正式允许的媒体/观察前缀/历史截止 | 是，所有阶段必须遵守 |
| `query_scope` | 题目明确要求统计或描述的对象范围、明确时间区间 | 决定计数与答案归属；默认观察也限制在此，需额外上下文时仍服从 allowed_scope |
| `search_hint` | 开头、结尾、靠近某场景、约某时刻等启发式线索 | 否，只影响优先级和初始窗口 |

本阶段纯视觉基线可以继续让明确的 `given_interval` 同时限制观察范围，保持 P01 既有严格行为；但不能把所有自然语言提示都自动当成这种硬合同。

不建议用一组更复杂关键词补丁解决。关键是**类型区分**，而不是把 `15s` 调成 `20s`。

### 2.5 `full_span_coverage` 不能继承为“事件/对象找全了”

当前 `build_coverage_manifest()` 根据抽样时间点和最大间隙计算 `full_span_coverage`，其中容许间隙来自 `max(0.5, 1.6 / sample_fps)`。这描述采样分布是否满足当前密度规则，不是事件识别召回率，更不是负证据的完整性证明。[G04]

新的共享层应分别记录：

```text
planned_scope_visited       # 计划覆盖的时间单元是否都执行过观察
actual_max_frame_gap_sec    # 实际进入模型的帧的最大时间间隔
required_resolution_met    # 是否满足此任务的预设分辨率/采样策略
unresolved_regions         # 模糊、遮挡、解码失败、输出截断区域
semantic_closure_status    # open / closed_under_policy / not_applicable
```

这里的 `closed_under_policy` 只代表“按预先固定的观察与复核策略没有未处理项”，不代表视频中真实事件的完备证明。尤其不能把 R1 的 `full_span_coverage=True` 直接用于 R3 的精确总数或 R4 的不存在结论。

### 2.6 现有历史诊断怎样使用

仓库的设计评审文档报告了三类历史机制问题：OCR 定位中发现的锚点在后续取证中丢失、跨阶段事实矛盾未形成足够强的约束，以及“看清颜色/主体”被误当成“看清选项所需的细节”。这些来自仓库对内部 smoke 的记录，不是本次重新运行或独立核验的 trace。[G07]

建议先做三项与 R1 定义直接相关的改进：

**锚点保真。** Locator 发现疑似 OCR/动作锚点时，保存原始 `frame_id + timestamp`。后续精看必须包含该原帧或能解释替换的重采样帧；不能只保留一句“附近可能有答案”。定位文本仍不能直接升级成证据，必须重读源帧。

**证据判别性。** 支持度同时检查目标可见、必要属性可见、关键选项差异得到证据支持。不是只检查 required slots 是否非空。

**矛盾登记。** 对同一主体、同一局部时段的相斥事实保留冲突记录。预算允许时回看；预算不足时降级支持度，不让最新文本静默覆盖旧证据。

“把选项判别条件提前到首次 Scout”可以作为独立消融，但不要悄悄改变 `p01-v2` 的严格选项盲基线，也不能仅凭三个历史错例宣称这种改变一定有效。

### 2.7 README 18 类范围的迁移建议

这是执行子型建议，不是已经逐样本验证的覆盖证明。[G01][F01]

| 原范围入口 | 在新体系中的处理 |

| Video-MME-v2 Visual Recognition | 直接可见 R1；遮挡追踪 R2；全范围否定 R4 |

### 2.8 R1 结论冻结条件

推荐先冻结 `R1-Visual/p01-v2`，保留旧结果和配置；对 scope/hint、锚点保真、证据支持度的修订另设版本。R1 的验收应基于明确筛选的直接取证子集，而不是“18 类均能启动并返回合法选项”。

## 3. 四类共用的运行协议

以下均为新设计，除明确引用的现有接口外，不声称仓库已经实现。

### 3.1 固定边界

本阶段默认只接收单个视频、问题、可选选项及正式允许的区间。所有语义角色均由同一个 Qwen3-VL-8B-Instruct 执行；控制器使用普通确定性代码做排序、区间运算、去重约束和集合运算。

不要求训练，不新增 YOLO、SAM、CLIP、专用追踪器或 ASR。视频画面中可见的文字可由 Qwen 读取；外部字幕、音轨转写、跨日历史库属于单独启用且单独报告的扩展，不默认为已经支持。官方模型卡可作为图像/视频调用的参考，但具体输入以仓库模型适配层和本次协议为准。[Q01][G10]

顶层 `pipeline_id` 由离线题目映射或调用方指定。编译器只识别该类内部操作和参数，不训练九类路由器。发现输入不符合本类时记录合同问题；不能在没有显式预算和接口的情况下偷偷切换到别的完整 agent。

### 3.2 输入结构

```json
{
  "request_id": "dev-video001-q03",
  "pipeline_id": "R3",
  "execution_subtype": "count_occurrences",
  "video_path": "/data/video001.mp4",
  "question": "How many times does the person place a cup on the table?",
  "choices": ["Two", "Three", "Four", "Five"],
  "allowed_scope": {"start_sec": 0.0, "end_sec": 60.0},
  "query_scope": {"start_sec": 0.0, "end_sec": 60.0},
  "search_hints": [],
  "input_profile": "visual_only",
  "benchmark_policy_id": "adapter-version-001",
  "budget_profile": "development-small",
  "group_id": "video001"
}
```

`execution_subtype` 可以来自预先人工整理的映射，但不能包含答案、GT 事件起止、GT 身份编号或正确选项。`allowed_scope` 只能来自官方提供给模型的输入协议。用于评估的证据标注不可被当成运行时裁剪信息。

### 3.3 共用源引用：模型只能引用它实际看过的材料

```json
{
  "evidence_id": "ev_0041",
  "source_id": "sha256-of-video",
  "frame_id": "v001-pts-51200",
  "timestamp_sec": 20.48,
  "pts": 51200,
  "time_base": [1, 2500],
  "view_id": "view_12",
  "call_id": "call_08",
  "bbox_xyxy_1000": [110, 220, 620, 900],
  "observation_status": "clear",
  "statement": "The cup rests on the table after being released."
}
```

这是目标 schema。具体 PTS 字段由解码器填充，模型不能自行编造。bbox 延续当前 P01 的 `normalized_1000` 约定；裁剪局部坐标必须转换回源帧坐标，保留裁剪变换。[G06]

模型返回时间优先使用媒体包中的帧 ID 或有明确映射的帧索引。控制器将其转换为原视频绝对时间。没有足够帧证明边界时，返回边界区间，而不是假造精确到毫秒的事件起点。

视频中的故事年份、字幕中叙述的历史时间，不能混进视频 PTS 时间轴。跨片段摘要中的先后也必须明确是呈现顺序还是故事顺序。

### 3.4 新增 LocalObservationService：只观察，不替调用方答题

```python
# 拟议接口；不是当前仓库已存在的类。
class LocalObservationService(Protocol):
    def observe(
        self,
        media: "MediaPacket",
        task: "ObservationTask",
        context: "RunContext",
    ) -> "ObservationBatch":
        """返回带来源的观察、未决区域、是否输出截断；不返回最终选项。"""
```

内部复用已有模型、源帧读取、图片/视频打包和协议修复逻辑；不要直接复用 P01 的终局 `solve()`。

观察结果至少包含：`facts`、`source_refs`、`unresolved`、`truncated`、`protocol_status`。JSON 解析失败不等于空观察；空观察也不等于“不存在”。

静态网格图适合导航和对象读取。动作边界观察必须保留时间顺序、真实时间戳和采样间隔；不能把不连续高分帧伪装成等速连续视频。支持按真实时间间隔打包的适配方式必须在开发阶段验证，不能仅因模型返回时间文本就认定对齐正确。

### 3.5 覆盖账本：不要只有一个 coverage 百分比

每个时间单元维护：

```json
{
  "tile_id": "tile_004",
  "core_interval": [15.0, 20.0],
  "context_interval": [14.0, 21.0],
  "status": "observed_needs_refinement",
  "source_frame_ids": ["f375", "f383", "f391"],
  "actual_max_gap_sec": 0.32,
  "spatial_resolution": [672, 384],
  "observation_call_ids": ["call_07"],
  "unresolved_reasons": ["event touches right boundary"],
  "output_truncated": false
}
```

分别报告：计划单元访问率、实际时间间隙、分辨率、解码失败区间、待复核区间、策略闭合状态。导航索引覆盖率不能计入语义观察完成率。极短事件、遮挡和模糊导致的不可见性应继续显式存在。

### 3.6 选项信息协议

默认首次观察不展示正确标签、选项编号或模型先前预测。R3 数值计数不展示候选数字，避免“看起来像某个答案”的计数。

但不能机械要求所有新任务都完全不看选项内容。例如“以下动作的正确顺序是什么”，目标动作可能只在选项中出现；“哪个物体没有出现”的查询集合也可能由选项定义。对此设定公开、固定的两种模式：

| 模式 | 允许内容 | 禁止内容 |
|---|---|---|
| `question_only` | 问题中的目标、范围和操作 | 所有选项内容 |
| `candidate_union` | 所有选项去标签、去排序后得到的目标/属性并集 | 哪个组合对应 A/B/C/D、候选顺序、正确答案和偏向某候选的检索 |

`candidate_union` 是新模板的明示协议，不是宣称仍与现有 P01 首轮严格选项盲完全相同。动作序列去重必须保留问题需要的语义差异；不能把“拿起”和“放下”合并成一个标签。

完整选项只在终局映射时使用。观察 prompt 不得要求“寻找支持选项 B 的证据”。

### 3.7 统一资源控制

一个问题只有一个 `RunContext` 和一份全局资源账本。所有观察、解析修复、边界回看、身份确认、摘要归并、终局重试共享该预算。

需要记录：模型调用数、实际输入/输出 token、实际视觉 token（适配层可提供时）、独立帧数、重复曝光帧数、裁剪数、累计像素、解码量、OOM 与降级。无法准确测量的字段标记为 estimated，不能与 measured 混为一谈。

计费/预算应在调用前预留、调用后核销。失败调用和 OOM 重试仍记账。模型后端若支持硬输出上限则使用；视觉预算按预处理后的实际图像/帧核对，而不是仅使用原始文件尺寸估计。

终局预留调用不能被前面的无限 repair 消耗。每个协议阶段最多一次修复；解析仍失败时保留未决状态，不生成“零事件”或“空集合”来冒充成功。

### 3.8 统一输出与失败语义

```json
{
  "prediction": "B",
  "pipeline_id": "R3",
  "execution_subtype": "count_occurrences",
  "completion_state": "budget_limited",
  "support_level": "partial",
  "answer_basis": "best_effort_from_observed_ledger",
  "evidence_consistent_values": [3, 4],
  "evidence_scope_closed_under_policy": false,
  "unresolved_reasons": ["boundary at 23 seconds not verified"],
  "evidence_ids": ["ev_01", "ev_02", "ev_03"],
  "resources": {},
  "trace": {}
}
```

最终 `prediction` 必须遵守 benchmark 输出协议；支持度和失败状态保存在 sidecar trace，不向只接受 A/B/C/D 的 evaluator 塞额外说明。

预算不足时可以按冻结规则输出 best-effort，但不能提高证据等级。完全无有效证据的确定性合法回退必须标记 `unbacked_fallback`。系统失败不自动等于选项“无法确定”，也不自动等于“没有出现”。

数值题在多个可能值之间如何产生单一预测应由适配器预先固定。该单值是估计，不可把 `[3,4]` 变成“已核实 3”。自由文本题预算不足时应避免“完整总结”等过强表述；官方格式不允许免责声明时，至少在 sidecar 报告范围不足。

### 3.9 缓存与跨题隔离

源帧、导航索引可缓存；cache key 包含媒体内容标识、解码参数、采样配置和实际时间范围。取缓存时仍必须校验当前 `allowed_scope`。

默认不跨题共享最终答案、选项判别结果或由另一道题引导生成的事实。需要共享问题无关的视频索引时，单独报告建库成本和摊销方法。Group-QA 中不能让后一道题看前一道题的预测或 GT；同组问题必须保持官方评估结构。

视频中或 OCR 读出的指令属于被分析内容，不得改变系统约束、工具权限或输出合同。

<a id="sec-4"></a>
## 4. R3：事件账本与时序归约

### 4.1 定位与统一流程

**目标不是让模型直接猜一个次数，而是让模型提供可复查的事件观察，由控制器完成时序操作。**

```text
问题与 benchmark 口径
  -> EventQueryCompiler：确定事件单位、范围、操作
  -> CoveragePlanner：生成覆盖计划与局部加密预算
  -> EventObserver：逐窗提取事件及边界证据
  -> BoundaryReconciler：连接跨窗事件、区分相邻重复事件
  -> EventLedger：冻结已确认及未决事件
  -> TemporalReducer：次数/顺序/首次/末次/时长
  -> OperationVerifier：检查该操作所需的范围与边界
  -> OutputAdapter：原生答案格式 + 诊断信息
```

这些是一个状态机中的阶段，不是分别独立维护调用预算的八个 agent。内部角色仍由同一个 Qwen 执行；能直接由代码完成的操作不再调用模型。

### 4.2 支持的执行子型

| 子型 | 事件状态 | 确定性主操作 | 不需要默认执行的步骤 |
|---|---|---|---|
| `count_occurrences` | 各次目标事件、边界、归属 | 计数独立 occurrence | 不必生成全片自然语言摘要 |
| `localize_event` | 满足描述的事件区间 | 输出区间或映射时间选项 | 不必统计所有无关动作 |
| `first_occurrence` | 候选首事件及之前的覆盖 | 取最早的可确定事件 | 后缀通常无须同等密度观察 |
| `last_occurrence` | 候选末事件及之后的覆盖 | 取最晚的可确定事件 | 前缀通常无须同等密度观察 |
| `order_events` | 各指定事件的时间记录 | 偏序/全序查询 | 不必发现视频中的每一种事件 |
| `next_after_anchor` / `previous_before_anchor` | 锚点、候选邻接事件及间隙 | 时间邻接查询 | 不预测尚未提供的未来 |
| `event_duration` | onset/offset 边界区间 | 时间差或时长比较 | 不把粗采样中心当精确边界 |
| `cooccurrence_frequency` | 主事件及参与者/伴随行为 | 按既定 episode 单位分组计数 | 不由频次直接推断动机或人格 |

“首次出现顺序”可以在账本中按类别取首次时间，不等于对类别做唯一计数。`next` 是完整可访问视频中的后继检索，还是对不可见未来的预测，由正式观察范围决定；后者属于 R7。

### 4.3 首先固定事件单位

同一段“切南瓜”视频可以有三种完全不同的问题：

```text
出现几段切南瓜的片段？       -> appearance_episode，R3
手完成了几次切下的动作？     -> action_cycle，R3，但感知要求更高
出现了几种不同的制作动作？   -> action_category，R4
```

MLVU 的 Action Count 构造包含将目标短动作片段插入长背景视频、统计其出现次数的设置。因此，不能看到 Action Count 就把一个连续片段中的每一次手部动作都计成一例。[B01] 对其他 benchmark，仍应使用其自己的任务定义。

建议 `EventSpec`：

```json
{
  "operation": "count_occurrences",
  "target_description": "the person places a cup on the table and releases it",
  "unit_kind": "action_cycle",
  "actor_constraint": "the foreground person",
  "object_constraint": "a cup",
  "query_interval": [0.0, 60.0],
  "start_criterion": "cup moves toward the tabletop while held",
  "completion_criterion": "cup rests on the table and the hand releases it",
  "reset_criterion": "a new placement begins after the previous one completed",
  "count_inclusion_rule": "completion_inside_query_interval",
  "censored_event_rule": "keep_unresolved_unless_policy_specifies",
  "repeat_policy": "count_each_visible_occurrence",
  "timeline_semantics": "video_presentation_time",
  "spec_source": "question_plus_versioned_benchmark_policy"
}
```

上述语义只是合成示例。开始/完成/重置条件必须能在当前视觉输入中核验，不能写成“人决定做某事”等不可见心理状态。若题目只问一次片段出现，不能自行增加必须完整展示动作起止的限制。

关于区间跨界和回放，必须由适配器明确：是“在范围内开始”“在范围内完成”“与范围相交”，还是官方另有规则；是在数视频中展示次数，还是现实事件次数。没有规则时保留口径歧义，不用一个全局默认值强行覆盖所有 benchmark。

### 4.4 核心状态结构

```json
{
  "event_id": "event_0007",
  "target_id": "target_cup_placement",
  "actor_id": "actor_local_1",
  "unit_kind": "action_cycle",
  "onset_bracket_sec": [18.08, 18.24],
  "offset_bracket_sec": [19.04, 19.20],
  "representative_frame_ids": ["f452", "f475"],
  "start_evidence_ids": ["ev_31"],
  "completion_evidence_ids": ["ev_35"],
  "reset_evidence_ids": ["ev_37"],
  "left_censored": false,
  "right_censored": false,
  "owner_tile_id": "tile_003",
  "observation_ids": ["obs_19", "obs_25"],
  "status": "accepted",
  "ambiguity_group_id": null
}
```

至少区分 `proposed`、`accepted`、`rejected`、`boundary_pending`、`identity_pending`。控制器生成稳定 ID；模型不得通过输出相同字符串擅自决定全局事件身份。

账本同时包含：`events`、`coverage_tiles`、`boundary_queue`、`conflicts`、`operation_state`。`event_id` 是事件发生实例，不能拿物体的 `entity_id` 替代：同一个杯子可能对应多个放置事件。

### 4.5 覆盖计划：密集与分层只改变观察计划

先把查询时间范围切成不重叠的 core cells，再给每个 cell 加可控上下文：

```text
core 0: [ 0, 10)      context: [ 0, 11]
core 1: [10, 20)      context: [ 9, 21]
core 2: [20, 30]      context: [19, 30]
```

core 的半开区间只用于确定唯一处理归属；视频事件真实区间仍允许跨 core。全部 context 必须在 allowed_scope 内。core 时间长度和帧数由任务分辨率、视频长度、预算共同决定，不固定成适用于所有视频的十秒。

**密集配置：** 相关范围较短时，所有 core 使用能辨认目标事件的采样策略，每个跨边界疑点进入回看队列。

**分层配置：** 范围较长时，先完成全部必需 core 的基础观察，再优先加密阳性、模糊、跨边界和快速变化区域。基础观察不能只看检索排名最高的两段。低分区域仍有最低覆盖，并按预设策略抽查非命中区域或安排更密的第二遍。

重要限制：低密度基础观察可能完全漏掉短事件。没有命中不证明该 cell 为负。能够保证的只是“按已记录的采样策略观察过”，不能保证“所有 occurrence 已被发现”。若任务要求的分辨率无法在预算内达到，输出 `resolution_limited`，而不是以零新增事件结束。

可以依据开发集标注确定某子型的采样策略；运行时不能读取当前测试题的 GT 最短事件时长来决定采样。

### 4.6 EventObserver：输出事件，不直接报全视频总数

输入为当前窗口媒体、EventSpec 和上一窗口必要的边界状态。上一窗口只传用于连接的少量事实，不传“当前已经数到几次，请继续数”这种强数值暗示。

输出包括：本窗口出现的事件候选、可见的开始/完成/重置证据、是否触及窗口边缘、不能判断的时间区域，以及是否因输出长度限制而截断。

建议 prompt：

```text
你是局部事件观察器，不是最终答题器。
只根据本次提供的视频帧，按 EVENT_SPEC 提取事件发生记录。

约束：
1. 不输出整个视频的最终次数，不选择答案。
2. 同一连续事件跨过当前窗口边缘时，标记 left_censored/right_censored。
3. 只有观察到 EVENT_SPEC 要求的独立开始、完成或重置证据，才区分相邻 occurrence。
4. 不把一个 appearance_episode 内部的多个动作周期误算成多个 episode。
5. 只引用当前媒体目录中的 frame_id；不能虚构时间、主体或帧。
6. 看不清、遮挡或采样不足写入 unresolved，不当成“未发生”。
7. 没有事件时也输出 observation_status；协议失败不能返回成功的空数组。
8. 若无法在输出限制内列完候选，设置 truncated=true 并指出需继续观察的范围。

返回 JSON：
{
  "events": [{
    "local_id": "...",
    "start_frame_ids": [],
    "completion_frame_ids": [],
    "reset_frame_ids": [],
    "actor_local_id": "...",
    "left_censored": false,
    "right_censored": false,
    "visible_statement": "..."
  }],
  "unresolved": [],
  "truncated": false,
  "observation_status": "valid"
}
```

主控制器用媒体目录计算边界 bracket。模型不能靠插值输出不可核查的细粒度时间戳。

### 4.7 跨窗连接与相邻事件去重

这是 R3 最重要的模块。建议按以下顺序处理：

**第一层：确定性同源重复。** 如果两次观察引用相同源帧、相同主体及同一个完成动作，优先判断为同一候选的重复观察。但同一帧也可能包含两名不同主体同时完成事件，因此不能只凭 frame_id 合并。

**第二层：连续性候选。** 一个事件在前窗右截断、在后窗左截断，且主体/目标相容，建立待连接关系，不立即合并。

**第三层：边界原片回看。** 取两窗之间的短连续视频，询问这是一件持续的事件，还是有“完成—重置—再次开始”的两个 occurrence。回看区域比整个原视频小，并且共享全局预算。

**第四层：保留歧义。** 无法判断时保留 `same_or_distinct` 关系，不凭时间距离或文本相似度强行决定。

不推荐仅凭 tIoU 或“相距小于一秒”合并：连续快速动作可能恰恰在很短时间内多次发生；同一个跨窗长事件又可能因采样稀疏而没有重叠观测。

事件确认后，按适配器的 inclusion rule 和一个确定的边界/锚点分配唯一 owner core。owner 不确定时事件留在 pending，不让两个窗口各贡献一次计数。

建议 BoundaryVerifier prompt：

```text
当前片段用于判断候选事件 X 与 Y 的关系。
请只判断：same_occurrence / distinct_occurrences / unresolved。

采用给定 EVENT_SPEC 的事件单位，不根据最终答案需要调整数量。
若为 distinct_occurrences，指出两次完成或一次重置的可见证据。
若为 same_occurrence，指出跨窗口连续性的可见证据。
仅引用本次提供的 frame_id。输出关系、证据引用、未决原因，不输出总数。
```

### 4.8 边界细化不是无条件二分搜索

只有已经确认“该短区间中存在一个特定的单次状态转移”，且判定条件在该区间内满足所需的单调性时，才可用二分式细化。

如果短区间内可能反复进入/退出、动作起止多次出现，二分会跳过事件。此时使用顺序滑动窗口加密，保留多转移可能性。

当查询边界截断动作时，不能把范围外帧作为默认证据补入。使用允许的上下文需符合 allowed_scope；真正不可访问的边界保持 censored，按官方计数口径处理。

### 4.9 TemporalReducer：从账本而不是自由生成中得到结果

#### 计数

统计被 inclusion rule 接受、独立身份已处理的事件。未决关系需要单独保留。

可输出 `observed_accepted_count` 和“证据相容的候选计数范围”。该范围的含义是：**在当前观察与身份假设正确的条件下**，账本允许哪些值；它不是对真实答案的严格置信区间。

如果存在未观察或分辨率不足的区域，最大可能漏检数通常没有依据，`upper_bound` 应为 null。不能机械使用：

```text
真实总数上界 = 已接受次数 + 未决候选数量
```

因为还有根本没有生成候选的漏检。模型误检同样可能让观察下界偏高，因此这些界限必须命名为 `evidence_conditional_bounds`。

#### 顺序

设两个事件的起点 bracket 分别为 `[a_lo, a_hi]`、`[b_lo, b_hi]`。只有 `a_hi < b_lo` 时，当前证据才足以严格确认 A 在 B 之前。区间重叠时保留并列/未决；不能默默比较中点伪造确定顺序。

如果问题定义以完成时间排序，使用 offset bracket，不能固定一律按 onset。

#### 首次与末次

首次查询需要确认候选之前没有更早的目标事件；末次查询需要确认候选之后没有更晚的目标事件。相关前缀/后缀必须达到预先定义的观察策略。可以从头向后或从尾向前扫描节省预算，但不能找到一个命中就宣称 first/last。

#### 锚点前后

先固定锚点是哪个 occurrence，再看相邻区间；出现多个相似锚点时不可任取一个。`first after` 必须检查锚点与候选之间是否还存在满足条件的事件，而不是检索最相似的后续片段。

#### 时长

若 onset 为 `[s_lo, s_hi]`，offset 为 `[e_lo, e_hi]`，可由代码计算：

\[
D_{\min}=\max(0,e_{\mathrm{lo}}-s_{\mathrm{hi}}),\qquad
D_{\max}=\max(0,e_{\mathrm{hi}}-s_{\mathrm{lo}}).
\]

边界被截断或无证据时，相关界限可能不可用。时长选择题若所有相容时长均映射到同一选项，可以结束；否则继续回看或输出低支持度估计。

#### 时间位置选项

“开头/中间/结尾/整段”等答案由各 benchmark adapter 的已核对定义转换。不能通用地把事件中点除以总时长，再默认用三等分作为官方真值定义。模板若含糊，就保留归属不确定性或使用经过验证的适配规则。[B02]

### 4.10 每个操作的停止条件

| 操作 | 必需审查的范围 | 可停止条件 | 不能用作停止理由 |
|---|---|---|---|
| 总次数 | 整个查询范围 | 策略覆盖完成，相关边界/重复关系处理，分辨率风险已报告 | 找到与某选项相同的数目 |
| 定位一个明确事件 | 足以唯一确定目标的相关范围 | 目标身份与区间符合问题，无未处理的竞争锚点 | 第一段语义相似片段 |
| 首次/末次 | 候选之前/之后的范围 | 所需前缀/后缀完成既定审查 | 最后一次检索命中 |
| 指定事件排序 | 所有指定事件及必要消歧范围 | 所有会影响答案的先后关系得到支持 | 用不确定时间的中点强行排序 |
| first after | 锚点到候选的间隙 | 锚点唯一，间隙按策略检查完成 | 找到任意 later 事件 |
| 时长 | 指定事件两端 | 边界精度已足以区分结果 | 已经看过事件中间 |

### 4.11 主状态机伪代码

```python
# 设计伪代码。各函数按本节合同实现，不是可直接运行的仓库代码。
def solve_r3(request, runtime):
    ctx = runtime.new_context(request)
    spec = compile_event_query(request, ctx)
    validate_event_unit_and_scope(spec, request)
    plan = plan_required_coverage(spec, ctx.budget)
    ledger = EventLedger(spec=spec, plan=plan)

    while ctx.budget.can_observe_with_terminal_reserve():
        action = ledger.next_action()
        if action is None:
            break

        if action.kind == "observe_core":
            batch = runtime.observe(action.media_plan, spec, ctx)
            ledger.record_observation_attempt(action, batch)
            ledger.ingest_valid_proposals(batch)
        elif action.kind == "verify_boundary":
            relation = runtime.verify_boundary(action, spec, ctx)
            ledger.apply_verified_relation_or_keep_pending(relation)
        elif action.kind == "refine_resolution":
            ledger.ingest_refinement(runtime.observe(action.media_plan, spec, ctx))

        ledger.recompute_operation_state()
        if ledger.operation_closed_under_policy():
            break

    frozen = ledger.freeze()
    value_state = temporal_reduce(frozen, spec)  # 代码：计数/排序/区间运算
    return runtime.render_with_support_status(value_state, frozen, ctx)
```

`next_action()` 的优先级必须保证必要基础覆盖不被大量局部回看饿死。推荐先为剩余基础单元预留预算，再在额外额度内处理边界；若覆盖和分辨率不可兼得，显式输出预算不足。

### 4.12 合成例题：跨窗口不能重复数

**下面是设计用合成事件，不是任何 benchmark 的原题/真实实验。**

问题：在 0–30 秒内，人把杯子放到桌上并松手多少次？候选为 2、3、4、5。

观察到：

| 事件候选 | 原视频位置 | 来自哪些窗口 | 处理 |
|---|---|---|---|
| X | 4.0–5.0 秒 | core 0 | 接受为事件 1 |
| Y1 | 9.5–10.5 秒 | core 0 的右上下文 | 边界候选 |
| Y2 | 9.5–10.5 秒 | core 1 的左上下文 | 与 Y1 原片回看，合并成事件 2 |
| Z | 22.0–23.0 秒 | core 2 | 接受为事件 3 |

结果不是四条 observation 就计四次。先生成三个独立 event，再按 inclusion rule 计数。如果第二次是否有完整松手看不清，应该保留 2/3 的证据相容结果，而不是因为选项有 3 就补全动作。

### 4.13 R3 的最小实现版本

第一版只做三种共享同一账本的操作：`count_occurrences`、`order_events`、`first/last`。随后扩展 duration 和邻接查询。episode 口径、跨窗边界和空观察语义必须第一版就有；不能等计数结果不好时再追加。

连续高速运动和复杂跨镜头重放消歧先标记 mixed，不应为了覆盖这些样本而把 R3 变成另一套通用 R2 追踪系统。

## 5. R4：清单构建与集合归约

### 5.1 定位与统一流程

**R4 数的是不同成员或核对成员关系，不是事件发生次数。** 其核心不是反复问“这一帧有几个”，而是把多次观察连接为一个有来源、可去重的集合。

```text
问题与集合口径
  -> InventoryQueryCompiler：确定 population、成员单位、筛选条件
  -> ScopeCoveragePlanner：单帧/局部场景/全片/已允许历史范围
  -> InventoryObserver：提取可见成员及来源
  -> EntityResolver：same / different / unknown 关系管理
  -> CanonicalInventory：建立实例、类别、文字或任务项清单
  -> SetReducer：唯一数量、成员关系、差集、分组比较
  -> CoverageAndIdentityAudit
  -> OutputAdapter
```

### 5.2 四种清单命名空间

| 命名空间 | 一个成员是什么 | 去重规则 | 示例 |
|---|---|---|---|
| `physical_instance` | 一个真实物体实例 | 有证据支持是同一对象才合并 | 多视角中的同一张桌子 |
| `semantic_category` | 一个任务定义的类别 | 采用冻结的类别规范和同义词表 | 三次跑步仍只是一种动作 |
| `text_value` | 一条文字值/名称 | 精确规范化或明确别名 | 同一店名出现多次只计一次 |
| `task_item` | 一个明确的计划或任务项 | 根据实体、数量、状态和显式修改记录 | 计划购买但尚未买到的物品 |

不能用同一套字符串归一化解决四者。两只杯子都被描述为“白色杯子”，不代表同一个 physical_instance；同一个杯子被描述为“马克杯”和“白杯”，也不代表两个实例。

### 5.3 InventorySpec

```json
{
  "operation": "count_unique",
  "member_namespace": "physical_instance",
  "target_category": "table",
  "qualifying_predicate": "visible in the room shown by the video",
  "query_scope": {"start_sec": 0.0, "end_sec": 90.0},
  "population_semantics": "physical_objects_visible_in_provided_video",
  "identity_policy": "evidence_supported_same_instance",
  "negative_claim_scope": "provided_observations_only",
  "normalization_policy_id": "tables-v1",
  "candidate_union": [],
  "quantity_semantics": "one_per_physical_instance"
}
```

`population_semantics` 必须遵循 benchmark 本身。上例是一个保守输入范围示例，不可擅自改写官方“房间内桌子总数”的任务定义：如果官方问房间总数，而视频没有展示足以支持全部对象的视角，就应记录证据不足，不能把“视频里看见的数目”说成“整个房间真实总数”。VSI-Bench 的 Object Count 是空间场景对象计数的实际入口之一，但多视角身份对应仍可能是感知瓶颈。[B03][F01]

### 5.4 原始观察与规范化实体必须分开

```json

  "frame_id": "frame_0240",
  "timestamp_sec": 9.6,
  "bbox_xyxy_1000": [80, 260, 470, 930],
```

`observation_id` 是“某帧里看到一次”；`entity_id` 是“推定的同一个真实实例”。将所有 observation 数量相加是错误的计数方法。

规范化实体保存所有观测及关系证据，不能只保存最终名称：

```json

  "entity_id": "entity_002",
  "member_namespace": "physical_instance",
  "category": "table",
  "observation_ids": ["objobs_004", "objobs_013"],
  "same_instance_evidence": ["paircheck_003"],
  "cannot_link_entity_ids": ["entity_001"],
  "identity_status": "supported",
  "attribute_conflicts": [],
  "qualifying_predicate_status": "satisfied"

```

### 5.5 观察计划

**单帧或开头局部场景。** 选取足以展示目标范围的原图/邻帧。若有“正在移动”的筛选条件，必须包含有序邻帧；不能单帧凭外观猜运动。必要时按网格或对象区域放大，但要统一源坐标和区域覆盖记录。

**跨视角场景。** 对相机进入新区域、视角转变和回访位置保留观察；基础计划仍覆盖范围，不只保留“看起来对象多”的帧。场景变化分数仅用于排序，不作为“这一帧没有新实体”的证明。

**全片文字/类别清单。** 先覆盖全部相关时段，再对疑似文字或新类别区域精看。快速闪现文字的漏检不能被“看过全部导航缩略图”抵消。

**计划与完成清单。** 只从正式允许的输入提取明确计划、完成、取消、替代等事实。若证据主要在音轨或历史对话，而当前仅提供视觉，则标记输入能力不足，不根据购物画面猜出之前讨论过什么。

### 5.6 处理一帧对象很多和裁剪重叠

每次观察设定对象输出上限是必要的，但必须有 `truncated` 和未完成区域。当上限用尽，进一步拆分空间区域或选择补充视角；不能让模型只列前十个，然后当作完整清单。

裁剪重叠时，把局部 bbox 转回源帧坐标，结合类别和重叠证据消除同一对象在两个 crop 中的重复观察。bbox 重叠只是候选关系，不对严重遮挡、嵌套对象或反射情形直接做硬合并。

同一时刻有两个位置明确不同的真实对象，通常可以建立 `different` 约束。但镜面、屏幕回放、图片中的物体是否计入，应遵循任务 population 定义；不能把反射直接当第二个真实实例，也不能无依据删除它。

### 5.7 EntityResolver：三值身份关系

不要一开始就对所有相似描述做不可逆 union。建议维护关系表：

```text
SAME：有支持同一物理对象的证据。
DIFFERENT：有支持两个不同对象的证据。
UNKNOWN：现有视角不能判断。
```

可用于形成候选配对的线索包括类别、稳定属性、邻近地标、时间连续性及原始画面位置，但这些只降低候选数，不自动证明身份。

配对流程：

1. 对新 observation 找同类别的少量可能对象；明确类别不符但分类不确定时仍保留复核机会。
2. 优先检查会影响最终计数或否定结果的身份疑点，避免所有对象两两比较。
3. 将两个对象 crop、各自原始画面上下文及时间信息共同提供给 Qwen；不能只给两句抽象描述。
4. 输出 `same/different/unknown` 和具体可见依据。
5. 只有支持度满足开发阶段固定规则、且不与已有 cannot-link 冲突时才接受 SAME。
6. 发现传递冲突时保留冲突组件并回看，不能让“最后一次判断”覆盖之前所有身份。

如果候选配对预算耗尽，未检查对象对保持 UNKNOWN。Top-k 筛选不代表其他对象一定不同。可将新对象暂记为独立 observation group，但不能自动把该 group 当成已确认新实体。

建议 prompt：

```text
判断观察 A 和观察 B 是否是同一个物理实例。
你会看到两个局部裁剪以及各自原图上下文和时间。

返回 same / different / unknown。
相同类别、相同颜色或相同名称本身不足以证明 same。
不同拍摄角度导致的外观变化本身不足以证明 different。
请引用支持判断的可见特征或场景连接；无法确认时返回 unknown。
不要为了得到某个总数决定身份；你不会看到最终计数选项。
```

### 5.8 集合归约与条件界限

对接受的 SAME 关系形成组件，同时保留 DIFFERENT 和 UNKNOWN。唯一数量至少应同时输出：

```text
observed_groups             # 当前观察组，不直接等于真实实例数
accepted_unique_entities    # 已充分确定的独立实例
unresolved_identity_pairs   # 会影响数量的身份疑点
evidence_conditional_bounds # 当前观测正确前提下的保守界限
```

在只考虑已观察对象且身份观察正确的条件下，每个 SAME 组件分别视为不同实体可形成一个上界；一组两两有 DIFFERENT 证据的组件可以提供一个保守下界。不要把某个启发式聚类结果称为全局最小/最大可行实体数，除非真的实现并验证相应约束求解。

存在未覆盖视角或可能漏检对象时，真实总体数量的上界应为 unknown。对于官方要求整个房间数量的问题，已观察对象上的界限仍只是证据条件下的界限。

对 `semantic_category` 和 `text_value`，主要任务是值规范化而不是物理身份：保留原文与规范值映射，大小写、空白和标点处理可以确定性执行；可能改变含义的同义词合并要有冻结的政策或回查证据。

### 5.9 否定题：未检索到不等于不存在

对于每个候选成员，维护至少四种状态：

| 状态 | 含义 | 能否直接当作“不存在” |
|---|---|---|
| `observed_present` | 存在明确正证据 | 否 |
| `checked_not_observed` | 所需范围按既定策略检查后未发现 | 只能在适配器规定的范围与观察假设下支持否定 |
| `unreadable_or_occluded` | 关键区域无法辨认 | 否 |
| `coverage_missing` | 相关范围没有完成观察 | 否 |

`checked_not_observed` 也不是物理世界中不存在的绝对证明。它的证据强度取决于范围封闭性、视角覆盖、分辨率和模型识别质量。

候选否定题可按去标签目标并集进行定向检查，但不得只为某个预期负例安排较少观察。最后的缺失检查应问“哪些候选尚无正证据、它们可能出现的区域是否真的检查过”，而不是要求模型“找到一个没有出现的答案”。

特别区分：

```text
画面中未出现某物       -> 视觉范围与实体清单
解说中未讨论某物       -> 需要允许的语音/字幕内容清单
现实场景中不存在某物   -> 不能仅由有限视频无命中推出
```

Video-MME 的原生 Object Recognition 中存在“未讨论的物品”式入口；它可以是 R4，但不因此成为当前纯视觉实现已支持的任务。[F01]

### 5.10 集合差集与数量差分

对于明确给出的计划清单 `P` 和明确完成清单 `D`，成员级结果可以由代码计算 `P - D`。

但下面几种情况不能靠简单字符串差集处理：

- 计划后来被取消或替换：必须有显式状态更新日志，按时间应用。
- 计划买三瓶、实际买两瓶：任务是数量差，不是成员是否存在。
- 不同人各自购买：清单应按人物作用域分开，不能混为一次完成。
- 购物车中出现不等于已经付款，拿起物品也不等于完成任务：谓词由题目定义。

基础 R4 可以支持明确的数量加减作为共享 reducer，但复杂任务优先级、隐含计划和未来安排不属于本阶段核心集。

### 5.11 InventoryObserver prompt

```text
你是清单观察器，不是最终计数器。
根据 INVENTORY_SPEC 列出当前媒体中每一个符合条件的成员观察。

要求：
1. 为同一画面中不同位置的对象分别返回 local_observation_id。
2. 引用 frame_id 和源坐标 bbox；说明可见属性与筛选条件是否满足。
3. 不把两个同类对象合并为一个，不给跨窗口对象擅自分配全局身份。
4. 对文字保留原文，不把近似拼写自动改为同一个名字。
5. 不把未知、遮挡、模糊标记成不存在。
6. 超出输出限制时设置 truncated=true，并列出尚未处理的空间/时间区域。
7. 不输出整个视频的最终唯一数量，不选择答案。

JSON 字段：observations、unresolved_regions、truncated、observation_status。
```

### 5.12 主状态机伪代码

```python
# 设计伪代码；不是已存在的仓库实现。
def solve_r4(request, runtime):

            inventory.apply_relation_if_consistent_else_keep_conflict(relation)
        elif action.kind == "audit_candidate_absence":
            inventory.record_targeted_check(runtime.observe(action.media_plan, spec, ctx))

        inventory.update_reducer_state()
        if inventory.query_closed_under_policy():
            break

    frozen = inventory.freeze()
    value_state = set_reduce(frozen, spec)
    return runtime.render_with_support_status(value_state, frozen, ctx)
```

### 5.13 合成例题：三次看见不等于三个新对象

**设计用合成例子，不是 benchmark 原题。** 视频前段同时看到桌子 A、B；相机绕到另一侧后又看到 A，以及疑似 C。

初始观察为四条：`A_view1`、`B_view1`、`A_view2`、`C_view2`。

先通过明确场景连接确认两个 A 是同一实例，清单剩三个观察组件。但 B 与 C 是否同一张桌子尚未知，所以不能立即宣布有三张。若没有其他漏检风险，当前观察下相容数量为 2–3。

随后回看 B 与 C 的上下文，发现一个在蓝沙发旁、另一个在门边，且补充视角同时展示两者，形成 DIFFERENT 证据。此时接受三张。如果补充画面仍遮挡，就保留未决；不能凭“颜色不同”自动断言不同，也不能因为都叫桌子自动合并。

### 5.14 R4 停止条件

| 子型 | 停止需要满足的条件 |
|---|---|
| 单帧实例计数 | 目标画面/区域按策略检查完，无输出截断，crop 重复已处理 |
| 跨视角唯一计数 | 范围观察完成，会影响答案的身份冲突已解决或不改变最终选项；未知漏检风险已报告 |
| 类别/文字值集合 | 值规范化政策固定，相关范围已检查，关键模糊文字已回看 |
| 未出现成员 | 候选状态完成，负项不是 unreadable 或 coverage_missing；闭合假设明确 |
| 计划差集 | 计划与完成证据范围明确，取消/替代及数量语义已处理 |

### 5.15 R4 的最小实现版本

建议先完成单帧/局部场景计数、文字值清单和有限候选否定检查，再增加跨视角身份关系。全屋同质对象计数应先作为 mixed 扩展评测，避免第一版就陷入三维重建和复杂追踪。

实体清单可以调用轻量局部运动验证，例如判断对象是否离开画面；但“同一只鸟多次离开是否只算一次”若离不开长时身份传播，就必须承认其 R2 感知依赖，不能把依赖隐藏在 R4 的一个普通函数名里。

<a id="sec-6"></a>
## 6. R5：分段全局综合

### 6.1 为什么它只是有条件的“证据组织型”

R5 不是纯确定性归约：从多段事实概括出“一个人准备并完成一道菜”仍需要语言理解和抽象。将它纳入，是因为可以通过完整范围观察、事实卡保存、限制摘要信息损失和回查，改善大量“只看局部就总结整体”的问题。

本阶段只支持**事实层面的综合**。不把“人物真正想表达什么”“为什么这个片段好笑”“影片的隐喻是什么”作为本流程已覆盖的能力；这些仍属 R6 或更复杂的关系解释。[F01]

MLVU 的 Video Summarization 是长视频关键内容概括入口，EgoSchema 和原表中的若干主线问题也可能需要较广泛的证据。原生任务名含 Topic Reasoning，不自动排除事实性全片概括；反过来，问“这个短片关于什么”也可能实际在问隐喻，需按执行子型区分。[B01][F01]

### 6.2 统一流程

```text
SummaryQueryCompiler：限定综合目标及不允许的推断
  -> CoveragePlanner：覆盖整个相关范围，而不是 Top-k 相关片段
  -> SegmentObserver：生成各段带来源的事实卡
  -> FactCardStore：保留原始事实、局部身份和未决区域
  -> HierarchicalMerger：受控分层合并，保留来源与重要差异
  -> GlobalComposer：形成事实梗概/全局选项判断
  -> ClaimAuditor：拆分全局陈述，核对来源与遗漏
  -> BoundedRevisit：必要时回到原片段
  -> OutputAdapter：答案 + 覆盖及支持度
```

摘要调用不能读取全部原视频来绕过覆盖结构；原片回看必须有明确目标、区间及预算。

### 6.3 支持的执行子型

| 子型 | 输出重点 | 越界例子 |
|---|---|---|
| `factual_video_summary` | 主要主体、可见事件、实际先后和结果 | 从行为推断没有明示的内心动机 |
| `global_activity_synopsis` | 整段视频总体做了什么，主要阶段是什么 | 只看一个动作就概括整个活动 |
| `content_genre_selection` | 依据内容结构判断教学/演示/采访等候选 | 仅根据画质或片头风格猜类别 |
| `multi_segment_factual_description` | 给定较大范围内多个阶段的合并描述 | 把跨片段共现自动写成因果 |

如果只是描述已定位的一个有限子场景，应继续使用 R1，而不是因为输出是长句就调用 R5。

### 6.4 SummarySpec 与分段规划

```json
{
  "operation": "factual_video_summary",
  "query_scope": [0.0, 180.0],
  "coverage_mode": "all_required_segments",
  "include_fields": ["main_entities", "main_actions", "observed_outcomes"],
  "timeline_semantics": "video_presentation_order",
  "allow_inferred_motives": false,
  "allow_causal_links_without_explicit_evidence": false,
  "output_language": "same_as_question",
  "output_length_policy": "benchmark_adapter",
  "preserve_opening_and_ending": true
}
```

使用镜头/场景变化辅助分段，同时设置最长 segment 时长，避免一个长镜头吞掉全部细节。没有可靠镜头检测时，等时长分段也是可接受的第一版；不要为“高级分段算法”引入未经预算的新模型。

短 segment 可以有必要上下文，但 core 不重复。分层归并中的覆盖范围使用 core 区间并集计算，不能把 overlap 重复算作额外覆盖。

`preserve_opening_and_ending` 指保留已经观察到的开场/收尾事实，不保证仅抽一张开头图就理解开场。模型未观察到的关键情节仍无法通过保存机制恢复。

### 6.5 SegmentCard：先保留事实，再压缩措辞

```json
{
  "segment_id": "seg_006",
  "core_interval": [75.0, 90.0],
  "observation_call_ids": ["call_10"],
  "local_entities": [
    {"local_id": "seg006_person1", "visible_description": "a person wearing an apron"}
  ],
  "facts": [
    {
      "fact_id": "sf_061",
      "statement": "The person transfers the cooked food from the pan to a plate.",
      "source_evidence_ids": ["ev_204", "ev_205"],
      "assertion_type": "observed",
      "support_status": "clear"
    }
  ],
  "local_transitions": [
    {"from_fact_id": "sf_060", "to_fact_id": "sf_061", "relation": "shown_before"}
  ],
  "new_or_rare_facts": ["sf_061"],
  "coverage_status": "observed_under_policy",
  "unresolved": [],
  "truncated": false
}
```

`new_or_rare_facts` 只是审查优先级，不是保证其全局重要。每段都要保存完整的有限事实卡；归并时可以不把全部文本塞回模型，但原始事实和来源必须保留在外部 store。

跨段实体身份不清时使用局部 ID，不把“都穿围裙的人”强行合成同一个人。若身份差异对梗概不重要，可以使用“有人/一名参与者”这种不会超出证据的表述；如果题目必须确定同一人物，就建立身份回查任务，而不是靠流畅语言掩盖问题。

### 6.6 SegmentObserver prompt

```text
你是视频分段事实记录员，不是全片总结器。
仅根据当前 SEGMENT 的可见内容返回事实卡。

请记录：主要可见主体、主要动作、明确结果、当前段与前后相邻动作的可见衔接。
每个事实必须引用当前媒体目录中的 frame_id。

不要：
- 根据常识补出没有展示的步骤；
- 推断人物动机、象征意义或隐藏因果；
- 因为知道最终问题而忽略当前段的重要不同内容；
- 对全片下结论，或选择最终选项。

请将模糊、遮挡、身份不明和输出截断单独标记。
返回 local_entities、facts、local_transitions、unresolved、truncated。
```

如果题目问整体行为，仍需要问题相关的观察重点，但不能让一个局部查询目标把其他主要阶段全部过滤掉。推荐固定字段加少量 query slots，而不是只提取与某候选答案相似的句子。

### 6.7 分层归并：不是反复对自由文本“再总结一次”

每次处理固定数量的子卡，例如最多四个。归并输入包含子卡的事实及必要来源索引，输出：

```text
parent_id
child_ids
covered_core_ranges
summary_claims[{claim_id, statement, supporting_fact_ids, assertion_type}]
protected_fact_ids
unresolved_conflicts
omitted_detail_index
```

所有父节点的子节点关系保存在控制器外部索引，不要求将一个小时内所有 frame_id 都放进模型上下文。某条摘要陈述只需携带其直接支持的事实 ID，控制器负责追溯到叶子来源。

归并规则：

1. 不新增子卡未提供、且没有新原片观察支持的事实。
2. 相邻卡描述同一个持续事件时可以合并措辞，但必须保留原时间范围和来源并集。
3. 语义相似但主体不同、结果不同或分属不同片段的事件不能仅为简洁而删除。
4. 数字、否定、身份和顺序有冲突时记录冲突；不要选择“听起来更合理”的版本。
5. 重要的开场设定、实际结果和明显不同的阶段应有保留位置，避免中间长段反复内容完全挤掉短结尾。
6. 摘要压缩不会替代原始 FactCardStore；后续审计可重新读取被摘要省略的叶子事实。

如果总事实量超过预算，必须报告压缩与覆盖风险。不能一方面截掉后半视频卡片，另一方面继续称“全片综合”。

建议 Merger prompt：

```text
你将收到若干相邻片段的事实卡。
请合并重复表述，形成这些片段的事实性概括。

每个 summary_claim 必须列出 supporting_fact_ids。
只能合并和改写已有事实；不得添加隐含动机、因果、主题寓意或未观察结果。
遇到冲突请写入 unresolved_conflicts，不要自行消除。
单独保留开场、结束、阶段转换和与多数内容明显不同的事实索引。
输出 child_ids、summary_claims、protected_fact_ids、unresolved_conflicts。
```

### 6.8 GlobalComposer 与选项核验

自由文本题：按照 benchmark 所需长度，将有来源的全局陈述组织成简洁梗概。输出中不能出现没有事实依据的连接词，例如仅因 A 后出现 B 就写“因此 A 导致了 B”。

选择题：最终才引入完整选项，把每个选项拆成可核验的内容声明，与全局事实匹配。包含多个子声明的选项，不能只因其中一半得到支持就判完全正确。

例如，一个选项写“先准备食材，随后烹饪并与朋友分享”，当前证据只支持准备、烹饪和摆盘，不能从“有两个人”自动推出分享。若另一个选项只是“演示一道菜的制作”，它的证据要求不同；比较必须基于实际事实，而不是长选项信息多就优先选择。

**Composer 仍是模型语义判断，不是形式化证明器。** 来源约束与回查可以发现部分错误，但不能把模型自己判定的“支持”当成绝对可靠。

### 6.9 ClaimAuditor 与有限回看

将草稿拆成原子陈述，对每条分配状态：

```text
supported_by_leaf_facts
conflicting_leaf_facts
unsupported_addition
requires_source_revisit
```

优先回看：决定选项差异的陈述、没有来源的数量/身份/因果词、片段间相互冲突的结果，以及开场/结尾覆盖不足的区域。

回看必须明确“要验证哪条陈述”，使用 LocalObservationService，而不是调用一次全片裸视频问答。回看结果更新叶子事实；仅重新生成受影响的父节点或相关陈述，避免一次回看触发整棵树全部重算。

预算耗尽后：删除无支持的新增陈述，缩小措辞范围，保留侧栏诊断。MCQ 必须作答时，按当前最有支持的选项输出，并把 unresolved 状态保存在 trace。不能让 Auditor 在没有新证据时反复自我认可，直到分数变高。

建议 Auditor prompt：

```text
核对 DRAFT 中每条陈述是否被 FACT_CARDS 支持。
对每条返回 supported / conflict / unsupported / revisit。
必须引用事实 ID；没有来源不能判 supported。
特别检查人物身份、数量、先后、结局和表示因果/动机的词。
你不能生成新视频事实。需要新观察时，只返回要验证的问题和候选时间范围。
```

### 6.10 覆盖与重要性的度量

分别报告：

- 计划 core 的访问率及实际抽帧间隔；
- 每个 core 是否形成有效事实卡，是否因解析/截断而缺失；
- 摘要每条陈述是否有叶子事实来源；
- 受保护事实是否被考虑、冲突是否保留；
- 回看次数和依然未处理的区域。

“每条摘要都有来源”不能证明没有漏掉重要内容；“所有 core 都有摘要”也不能证明每段观察正确。这两个限制都应在评估中保留。

跨段支持覆盖时使用时间区间并集，而不是重复观察次数。反复播放同一个短段，不应该使它在全局重要性上获得额外时长权重。

### 6.11 主状态机伪代码

```python
# 设计伪代码；不是已经实现的 API。
def solve_r5(request, runtime):
    ctx = runtime.new_context(request)
    spec = compile_summary_query(request, ctx)
    validate_factual_synthesis_scope(spec)
    plan = plan_all_required_segments(spec, ctx.budget)
    store = FactCardStore(plan=plan)

    for segment in plan.segments:
        if not ctx.budget.can_map_with_merge_and_terminal_reserve(store, plan):
            store.mark_remaining_unobserved()
            break
        card = runtime.observe_segment(segment, spec, ctx)
        store.commit_valid_card_or_failure(segment, card)

    tree = merge_cards_with_lineage_and_budget(store, spec, ctx)
    draft = compose_from_cards(tree, store, spec, ctx)
    audit = audit_claims_against_leaf_facts(draft, store, ctx)

    for issue in audit.priority_revisit_issues:
        if not ctx.budget.can_revisit_with_terminal_reserve():
            break
        observation = runtime.revisit_source(issue, spec, ctx)
        store.update_affected_facts(observation)
        tree.update_affected_nodes_only(store, observation, ctx)

    return finalize_without_unsupported_additions(draft, tree, store, spec, ctx)
```

如果基础 map 的所有段无法完成，应优先保证输出诚实反映覆盖不足。把未看区间偷偷用通用剧情常识填上不是降级方案。

### 6.12 合成例题：把全片事实组织起来，不添加动机

**设计用合成示例，不是原论文题目。** 90 秒视频有三个阶段：

| 段 | 局部事实卡 | 可进入全局概括的内容 |
|---|---|---|
| 0–30 秒 | 清洗并切分蔬菜 | 准备食材 |
| 30–65 秒 | 将食材放入锅中翻炒 | 烹饪过程 |
| 65–90 秒 | 将食物盛盘，展示成品 | 摆盘与成品展示 |

合适的综合：“视频展示了从蔬菜准备、锅中翻炒到盛盘展示的制作过程。”

不合适的补充：“主角为了讨好朋友，学习了一道健康食谱。”除非视频另有明确证据，这种说法需要动机/社会关系推断，不属于事实综合。

若最后 25 秒因为预算不足未观察，只能说“已观察内容包括准备和烹饪”，并在 trace 记录结尾缺失，不能自动补出盛盘、品尝或成功结果。

### 6.13 R5 停止条件与最小实现

结束前应满足：所需 core 按策略观察，事实卡无未标记截断，最终主要陈述都有来源，关键冲突处理，必要的开头/结尾证据没有被压缩静默丢弃。任何一项未满足均可 best-effort 结束，但必须保留不足状态。

第一版可采用等时长分段、固定大小事实卡、两级合并及一次集中审计。不需要先实现复杂知识图谱、学习型记忆压缩器或多模型评审。长视频超出两级容量时再扩展同一个分层结构，而不是新增一个“超长视频 pipeline”。

| P01 解析与重试思路 | 统一到全局 budget wrapper | 每个角色自行 repair 导致累计超预算 |
| P01 的 Top-2 候选选择 | 仅用于局部查找或回看优先级 | 不适用于全片计数、清单或全局综合的基础覆盖 |
| `P01VideoAgent.solve()` | 保留给 R1 单题任务 | 不作为每窗“观察子程序” |

现有 `BaseVideoModel.generate()` 接受 messages、videos、images 和扩展参数，返回 `ModelOutput(text, metadata)`；新的观察服务可在这一层构建，不需要改动模型训练方式。[G10]

### 7.3 RunContext 中的状态与调用边界

```python
# 拟议的结构示意。
@dataclass
class RunContext:
    request_id: str
    budget: "GlobalBudgetLedger"
    frame_catalog: "FrameCatalog"
    evidence_store: "EvidenceStore"
    coverage: "CoverageLedger"
    trace: "TraceWriter"
    model: "BaseVideoModel"
```

所有调用通过 `runtime.call_model(role, media, prompt, ctx)` 进入。该函数统一执行预算预留、源范围检查、模型调用、JSON 解析、最多一次修复、来源验证、实际资源核销和 trace 保存。

来源验证至少检查：事实帧属于当前调用，时间在允许范围，bbox 合法，事实引用 ID 存在，局部坐标转换无误。来源合法不证明语义正确，二者分开记录。

### 7.4 建议预算：可运行前需要用实际环境校准

现有 P01 原生配置为最多 20 次模型调用；这是一项已存在的配置事实，不是新流程最优预算。[G05]

给新模板的开发预算可先采用下面的**示例配置**。它不承诺特定 GPU 无 OOM，也不是推荐的正式 leaderboard 配置：

```yaml
# 建议新增配置的概念字段；当前仓库未必接受这些字段。
profile_name: evidence-development-v1
max_model_calls: 32
terminal_call_reserve: 2
protocol_repair_attempts_per_stage: 1
max_video_frames_per_call: 32
max_detail_images_per_call: 2
max_output_tokens_observer: 1536
max_output_tokens_merge: 1536
max_output_tokens_final: 512
max_boundary_or_identity_rechecks: 6
max_summary_source_revisits: 3
max_emitted_observations_per_call: 32
on_observation_overflow: split_region_and_mark_pending
```

此外必须在运行环境中填写并验证：每次/每题视觉 token 硬上限、文本上下文上限、累计媒体曝光上限和实际像素预处理设置。不应使用一套未经测试的固定显存值作为所有机器的默认“安全保证”。

上表的 32 帧仅是新模板的小预算起点，**不是给已有 P01 动态模式强加统一截断**。与原 P01 的比较应另设共同评测预算，并冻结双方实际资源配置。

### 7.5 预算可行性在观察前检查

R3/R4 需要覆盖 `N` 个基础窗口时，设编译成本为 `C_compile`，基础观察为 `N` 次，预留复核为 `C_verify`，终局为 `C_final`，则至少检查：

\[
C_{\mathrm{compile}}+N+C_{\mathrm{verify}}+C_{\mathrm{final}}
\leq C_{\mathrm{max}}.
\]

协议重试会额外消耗已预留预算，不能在这个式子之外免费发生。该式只约束调用数量，视觉 token 和累计曝光仍需独立满足限制。

R5 以最多四个子节点归并、16 个基础片段为例：16 次 map，4 次第一层 merge，1 次根 merge；另加编译、composer、audit 和预留回看。控制器应在开始前确认预算，而不是 map 用完 30 次后才发现没有预算做合并。

如果视频很长且目标事件极短，小调用预算不可能同时提供高密度全范围观察。合理降级是标记 `budget_limited` 或 `resolution_limited`，不是宣称分层检索天然解决了采样遗漏。

### 7.6 OOM 与协议失败

OOM 重试可以降低空间分辨率或拆分批次，但需要记录变化。R3 对短事件敏感时，不能只为省显存降低时间采样、却仍声称满足原事件分辨率；OCR 对小字敏感时也不能降低到看不清后继续给 strong。

对 R3：失败窗口进入 coverage_missing，不贡献“零次”。

对 R4：失败区域保留 unknown，不贡献空集合或不存在证据。

对 R5：失败段保留缺失标记，不生成通用摘要填充。

对于无法加载媒体等输入错误，应走统一错误协议。benchmark 强制输出占位预测时，仍在 sidecar 保留输入失败，不能与正常答题混淆。

### 7.7 部分结果与检查点

每个窗口观察、边界关系更新、实体关系更新和摘要节点都可写入 append-only trace。恢复运行时校验媒体 hash、模型/配置/提示词版本和 allowed_scope，防止不同版本证据混入同一个账本。

只有正式完成验证的更新才能改变 accepted 状态。建议观察 batch 先作为临时记录，来源与 schema 校验通过后再提交；失败的半个 batch 不应一边触发 repair、一边已经改变总数。

### 7.8 首版不要增加的组件

不新增训练型路由器，不为每个 benchmark 写独立 agent，不让一个类维护多套互不兼容的总控制流，不用 GT evidence 帮检索，不引入第二个强模型当免费裁判，不建立与当前题目无关的全视频巨型知识图谱。

需要复杂能力时先记录真实依赖；不要用“调用一个工具”这一描述隐藏尚未实现、未经验证的追踪、音频理解或场景重建系统。

### 8.2 R3 候选入口

| Benchmark | 可考虑的原生入口 | 必须进一步确认的条件 |
|---|---|---|
| MLVU | Action Count、Action Order | AC 的单位按插入片段/出现 episode，而不是一律按内部动作周期；AO 指定目标的排序 |
| MVBench | Action Count、Action Localization、Action Sequence、Character Order、Scene Transition | 事件可识别；Character Order 的 OCR 与首次时间都需证据 |
| TVBench | Action Localization、Action Sequence、Egocentric Sequence、Scene Transition、Unexpected Action | Unexpected Action 要求定位部分，不是解释异常；定性事件识别可能仍是 mixed |
| LVBench | Temporal Grounding 的定位/时长/顺序子型；Event Understanding 中的次数子型 | 给定时段只问发生什么仍走 R1；六种能力标签不能视为互斥执行类型 |
| LongVideoBench | Event before/after Event、Event before/after Text、Object before/after Object、Object before/after Text、Sequence of Scenes | 文本锚点依赖是否为画面可读文字/正式允许字幕；当前纯视觉模式不支持缺失的外部字幕证据 |
| Video-MME | Temporal Perception 中真正关于视频时间的子型；Counting 中事件次数子型 | 叙述的历史年代不是视频出现顺序；不能将整个原生标签硬归 R3 |
| Video-MME-v2 | Event Sequence Ordering、Object Appearance Ordering、Repetitive Action Counting、Temporal Action Localization；Basic Counting 的事件次数子型 | first/last/after 的覆盖范围；同一 Basic Counting 还含实例数量，后者 R4 |
| VSI-Bench | Appearance Order | 按类别首次出现排序，使用允许的完整视频范围，不把题干 will 当作预测 |
| TOMATO | Action Count、Visual Cues | 轨迹识别、动作起止可能强依赖感知；Visual Cues 的视觉条件不授权额外音频 |
| EgoLifeQA | HabitInsight、RelationMap 中的频次；EventRecall 中的时间邻接 | 仅作为允许历史访问扩展，当前单视频纯视觉首版不能宣称支持跨日历史/语音 |

TOMATO 轨迹计数、复杂动作微小边界、主观“最有趣部分”定位不应默认计入 organization_core。它们可以使用同一账本模板，但需要单独报告局部事件识别能力。

### 8.3 R4 候选入口

| Benchmark | 可考虑的原生入口 | 必须进一步确认的条件 |
|---|---|---|
| VSI-Bench | Object Count | 场景实例数量；跨视角身份不确定性，不能把相机转回造成的重复画面累加 |
| MVBench | Moving Count；Object Existence 中的全范围否定 | 区分不同离开对象与离开次数；运动筛选可能需要 R2 式局部组件 |
| TVBench | Object Count；Action Count 的条件候选 | 前者可能要求开头正在运动的金属实例；后者计数单位仍需核对 |
| Video-MME | Counting Problem 的实例/类别比较；Object Recognition 的未出现/未讨论；OCR 的全范围唯一文本 | “未讨论”需要对应模态；数量比较应建立各类清单而不是直接猜最多 |
| Video-MME-v2 | Basic Counting 的实例数量；Entity Existence Change Detection 的不同鸟数量；Visual Recognition 中的范围否定 | 同一个原生标签可能混合 R3/R4/R2，不以标签强绑定 |
| LongVideoBench | Scene-referred Object Existence 中的 did not appear | 否定范围可能只是指定场景，不应无条件扩大到全片 |
| LVBench | Entity Recognition 中实体根数；Key Information Retrieval 的完整关键字集合 | “几根香”是实例；一处年份读取仍 R1 |
| EgoLifeQA | TaskMaster 中明确计划减已完成 | 跨日历史/文本输入属于扩展；任务状态与数量规则要明确 |

**TVBench Action Count 保留待审。** 工作簿和原论文模板中的 sets/distinct repeated actions 表述不足以单凭文字消除“组、动作种类、重复次数”的差异。因此，不将它批量标成 R3 或 R4 核心集；应抽看官方视频及标注口径后固定适配规则。[B02][F01]

### 8.4 R5 候选入口

| Benchmark | 可考虑的原生入口 | 仅纳入的子型 |
|---|---|---|
| MLVU | Topic Reasoning、Video Summarization | 全片活动/内容事实概括 |
| Video-MME | Information Synopsis | 事实性主线、内容体裁、主要活动；列表任务转 R4 |
| LVBench | Summarization；Event Understanding 中的整体概括 | 多段事实综合；只问锚点后局部事件仍 R1/R3 |
| EgoSchema | Long-form Video QA 中整体行为概括 | 广泛证据支持的行为总结；隐含动机和关系转 R6 |
| 其他原生入口 | 问题实质确为多段事实描述时 | 不因生成文本或视频很长就自动归 R5 |

Video-MME-v2 的 Symbolic/Metaphorical Interpretation 即使题干形式像“短片讲什么”，仍不能整类纳入事实综合。本阶段不宣称解决寓意推断。[F01]

### 8.5 对代表题的证据依赖做一次离线审查

最有价值的人工工作不是再写几十个类别名，而是给开发样本补四项：

```text
count/member unit        # 数的是 occurrence、实例、类别还是文字值
minimum evidence scope   # 局部、前缀、后缀、全范围或多视角
input dependency         # 视觉、画面文字、外部字幕、音频、历史
perception bottleneck    # 普通可见 / 细动作 / 遮挡身份 / 尺度与空间 / 语义解释
```

这些标记能解释为什么某题应该用当前模板，也能解释失败是否真的属于 pipeline 的责任。为 benchmark 标注的最小证据范围只用于开发诊断和评估，不能把测试题的人工定位直接作为正常运行输入。

### 9.2 共享层必须先通过的测试

使用 FakeModel/合成媒体目录可以测试控制器逻辑，不需要 GPU。伪造的观察只用于单测，不能进入真实 benchmark 答案生成。

| 测试 | 合成输入/行为 | 预期 |
|---|---|---|
| 硬范围越界 | 模型引用 allowed_scope 外的帧 | 引用拒绝，记录错误，不进入证据 |

| Crop 来源 | 两个重叠裁剪引用同一物体 | 坐标回映正确，不因 crop ID 不同自动算两个 |
| 观察截断 | 达到每调用对象/事件上限 | truncated=true，相关范围 pending |

### 9.3 R3 必测案例

| 场景 | 必须得到的行为 |
|---|---|
| 一次事件跨两个窗口 | 两条 observation 最终归一个 event，不重复计数 |
| 两次事件相距很短 | 有重置/完成证据时不得因时间近而合并 |
| 连续长动作片段 | appearance_episode 模式不按每个内部周期重复计数 |
| 同一对象执行多次 | 多个 event，共用实体 ID 不会压成一次 |
| 两个主体同时动作 | 主体条件区分；不能因同一帧而合并 |
| 动作恰好跨查询起点/终点 | 按固定 inclusion rule；censored 不被静默删掉 |
| 查询 first | 没检查必要前缀不得标强支持 |
| 查询 last | 没检查必要后缀不得标强支持 |
| 时间 bracket 重叠 | 不以中点假造确定顺序 |
| 快事件落在抽样间隙 | 标记 resolution risk，不声称采样覆盖即可保证零漏检 |
| 回放/重演 | 根据固定 repeat_policy 处理，不能一律当重复观测去重 |
| 边界复核失败 | 保留未决关系和条件计数，不随意补齐到最近选项 |

### 9.4 R4 必测案例

| 场景 | 必须得到的行为 |
|---|---|
| 同一实例在多帧出现 | 有同一证据时只计一次 |
| 两个同色同类对象同框 | 作为不同实例，不按描述字符串合并 |
| SAME 传递与 DIFFERENT 冲突 | 不产生自相矛盾的身份组件，进入冲突复核 |
| UNKNOWN 身份 | 不是自动新实体，也不是自动同一实体 |
| 模糊文字 | 保留原文候选与不确定性，不静默“纠正”成已知名字 |
| 区域未看完 | 未出现项状态为 coverage_missing，不是 absent |
| 镜像/屏幕回放 | 根据 population 定义处理，不能随意双计或删掉 |
| 离开场景又回来 | 唯一实例数与出入事件次数不混淆 |
| 动作类别集合 | 同动作多次只计一个类别，除非任务单位定义不同 |
| 计划三件实际两件 | 数量差分与成员差集分开 |
| 计划取消/替换 | 只按明确更新证据改清单，不按常识猜意图 |
| 所有对象输出到上限 | 不将模型输出上限误当实际对象总数 |

### 9.5 R5 必测案例

| 场景 | 必须得到的行为 |
|---|---|
| 中段冗长、结尾很短 | 已观察到的关键结尾不能因长度短被无痕删除 |
| 两段重复画面 | 覆盖及重要性不因 overlap 重复累加 |
| 某段解析失败 | 留缺失记录，不用通用摘要填充 |
| 摘要写出未出现的结局 | Auditor 标 unsupported，删除或回看 |
| 先后被写成因果 | 无明确依据时拒绝因果措辞 |
| 两个人物外观相似 | 不强行合并身份；必要时使用不超出证据的表述 |
| 子卡之间数字相冲突 | 保留冲突，不靠自然语言平滑成一个数字 |
| 部分全局选项成立 | 不能只核验一半子声明就接受整个选项 |
| 摘要层级增加 | 每条父陈述能追到叶子来源，未保留的细节有索引可回查 |
| 要求解释隐喻 | 记录 out-of-scope，不伪装成已经解决的事实综合 |

### 9.6 与什么基线比较

至少保留四种设置，固定模型、输入模态和正式允许的观察范围：

| 设置 | 作用 |
|---|---|
| Budget-matched Direct | 在同等资源上限下直接读视频并答题，衡量复杂流程是否值得 |
| Retrieval/Iteration without Ledger | 允许迭代观察，但不维护事件/实例结构，分离“多看几次”与“结构化状态”的收益 |
| 完整 R3/R4/R5 | 本文设计 |
| 诊断用 oracle evidence | 仅在独立诊断实验中提供人工正确局部证据，定位感知瓶颈；不能混入正常 benchmark 分数 |

进一步可做“oracle 结构化账本 + 确定性 reducer”的离线单测，用来确认归约器本身没有逻辑错误。这是控制器正确性诊断，不是一个可部署的视频问答系统。

只有在正确片段给定后局部事件/对象仍经常辨认错误，才有依据判断该样本的主要瓶颈是感知。反之，局部正确而全局错误，优先检查范围、去重、顺序和压缩。

### 9.7 最重要的消融

**R1：** 保持原 P01；仅修正 scope/hint；再分别增加锚点保真、判别性支持检查；提前引入选项判别另作独立实验，不与所有改动混为一次。

**R3：** 无跨窗连接；仅时间重叠合并；有边界复核；无基础覆盖保留的 Top-k 检索。重点观察漏计/重计是否按预期变化。

**R4：** 帧计数直接相加；按文本名称去重；三值身份关系；去掉负证据覆盖检查。重点观察回访视角和同质对象。

**R5：** Top-k 片段摘要；全范围平铺事实卡；带来源分层合并；增加关键陈述回看。重点观察覆盖、结尾遗漏和无支持新增内容。

所有消融应计入真实调用与曝光成本。如果“加边界复核”的版本只是多用了很多帧，必须另做等预算比较，不能把全部收益归因于账本设计。

### 9.8 应报告的指标

| 层级 | 指标建议 | 解释 |
|---|---|---|
| 官方任务 | 各 benchmark 的原生 accuracy/数值/生成式评分 | 不擅自用自己的 confidence 代替官方分数 |
| 成本 | 调用数、视觉/文本 token、媒体曝光、运行时间、OOM/修复 | measured 与 estimated 分开 |
| 支持度 | supported / partial / unbacked_fallback 分布 | 不能只展示成功且证据强的样本 |
| R3 诊断 | 事件漏计/重计、边界误差、顺序错误 | 需要相应人工事件标注；没有标注时标 N/A |
| R4 诊断 | 重复实例误计、错误合并、UNKNOWN 比例、负项覆盖缺失 | 需要身份或集合级标注才可计算相应准确率 |
| R5 诊断 | 覆盖缺失、无支持陈述、主要事实遗漏 | 人工或独立评估，不把模型自审直接当真值 |
| 归因 | 检索/观察/去重/归约/输出协议错误 | 一个样本可以记录多个阶段错误 |

对于 Video-MME-v2，保留原始题目组以及官方 grouped evaluation；只评估其中一部分 R 类型不能冒充完整原生分数。[B04] 其他 benchmark 的评估器、数据版本及许可输入也应固定版本记录。

### 9.9 划分与统计原则

同一视频及其题目组放在同一划分，避免调参视频泄漏到测试。对外报告时保留：全量题数、符合本输入模式的题数、organization_core 数、mixed 数、合同失败和资源失败数。

可以对核心子集另报性能，但必须在正式测试前固定筛选规则；不能把错题事后改成“其实是感知题”然后从分母中删除。

不同长度、事件密度、重复程度、同质对象比例和字幕依赖应分别统计。平均准确率可能掩盖“短视频很好、长视频预算根本不够”或“普通对象有效、同质对象失败”的真实边界。

### 9.10 验收门槛的设置方式

控制器不变量应全部通过单测，包括范围、时间戳、预算、来源、空观察和跨窗去重；这是可以设硬门槛的部分。

准确率提升、速度、幻觉率、事件召回等效果门槛，应先通过固定开发集估计再冻结。本文不凭空给出“必须提升 10 个点”或“覆盖率达到 95% 就足够”的数字。正式比较使用预先定义的指标，并报告样本数和不确定性。

## 10. 开发顺序与冻结标准

### 10.1 推荐顺序

**阶段一：冻结 R1-Visual 基线并整理共享合同。** 保留原提交结果，明确输入范围、单段证据、选项盲和必答回退。优先修复 scope/hint 类型边界，补齐来源和资源测试；这些改动单独记录版本。

**阶段二：做 R3。** 它与已有局部事件观察关系最直接；先实现可观察事件的 count/order/first/last，共享一份事件账本。不要先把所有高速运动、频率、相位问题拉进来。

**阶段三：做简单 R4，再扩展跨视角。** 先通过单帧/局部场景、文字值集合和有限否定清单的测试；随后引入三值身份关系。复杂同质对象和遮挡追踪保留 mixed 评估。

**阶段四：做 R5 的事实综合。** 先完成覆盖分段、事实卡、来源归并及一次集中审计；再扩展更长视频层级。推断人物动机或寓意不作为这阶段的优化目标。

这是依赖顺序，不是工期估计。每阶段都应有独立可复现配置，不能只留下不断变化的一份“大一统最新版”。

### 10.2 每个模板应交付的最小文件/接口

| 项目 | 必须明确的内容 |
|---|---|
| 范围文档 | 支持子型、输入模态、计数/集合口径和排除条件 |
| 数据结构 | 原始观察、规范状态、未决状态、来源引用 |
| 控制器 | 有限循环、全局预算、覆盖优先级、终局策略 |
| 观察 prompt | 不猜总答案、允许 unknown、支持输出截断 |
| 确定性 reducer | 与观察模型解耦，可用合成账本单测 |
| trace | 所有调用、原始输出、媒体、更新原因、失败和实际资源 |
| 评测适配 | 原生答案格式、官方范围规则、group/video 划分 |
| 测试 | 正常、跨边界、空观察、预算失败与对抗性歧义 |

### 10.3 什么时候应重新合并或拆分

如果两个执行子型只是在 reducer 上换一个确定性函数，核心状态和控制流相同，就继续放在同一主模板；例如 R3 的 count 和 order。

如果某个子型必须长期维护另一种关键状态，且失效机制稳定不同，应明确混合依赖或另归主类。例如 R4 对象计数若需要完整遮挡身份传播，不应在 identity.py 里无限堆出一个未命名的 R2。

如果所有改进都只来自多抽帧，结构化状态没有额外效果，则应简化流程，不为了凑“pipeline 创新”保留无收益模块。

### 10.4 最终工程建议

保留一个已经可运行的 R1-Visual 基线，新建三个主控制器，而不是从零重写四套完全独立的系统：

```text
R1：找到关键局部证据 -> 直接事实核验
R3：覆盖必要范围 -> 事件账本 -> 时序归约
R4：覆盖必要范围 -> 去重清单 -> 集合归约
R5：覆盖相关全局 -> 分段事实 -> 可追溯综合
```

共享的是源帧、模型、观察服务、范围合同、预算和来源检查。不同的是需要保存的主状态，以及足以支持答案的停止条件。

**本阶段要证明的，不是模型突然学会了更强的视觉或推理，而是相同模型在受控观察预算下，是否更少漏掉证据、更少重复计数、更少混淆身份、更少在摘要里补出没有发生的事情。**
